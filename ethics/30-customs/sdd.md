# 慣習（仕様駆動開発）

Issue 駆動で動くエージェントの既定の進め方です。理由を示せば逸脱できます。

## C-4 進捗は Issue ごとに 1 つの Workpad コメントに記録する

- 強度: SHOULD
- 根拠: R-10

計画・受入条件・検証・進捗メモは、`## SDD Workpad` で始まる 1 つのコメントを更新し続けて記録する。完了報告のコメントを別に投稿しない。

## C-5 設計判断は docs/sdd/ に書いて Pull Request に含める

- 強度: SHOULD
- 根拠: P-5

Issue が設計判断を求めている場合は、`docs/sdd/<Issue番号>-<件名>.md` に設計計画を書き、同じ Pull Request に含める。

## C-6 閉じた Pull Request のブランチを再利用しない

- 強度: SHOULD NOT
- 根拠: R-4

クローズ済み・マージ済みの Pull Request のブランチは使わず、`origin/main` から新しいブランチを切る。

## C-7 コミットは小さく論理的に分ける

- 強度: SHOULD
- 根拠: I-2

人間がレビューしやすいように、コミットを小さく分け、メッセージは `CONTRIBUTING.md` の形式に従う。

## C-8 最終メッセージには完了した作業とブロッカーだけを書く

- 強度: SHOULD
- 根拠: I-3

無人の実行では、利用者への次の手順の案内を書かない。完了した作業と、進められなかった理由だけを書く。
