# DSPy における支配構造の再現

状態: 承認済み（2026-11-20、Pull Request 8 番のマージによる）。段階 1 は実装済み（実 LM での実行を除く）。段階 2、段階 3 は未着手

## 背景と目的

[倫理階層](../../ethics/README.md)は、規範を 理念 > 原則 > 規則 > 慣習 の 4 層に分け、上位が下位を支配する関係を定めています。`ethics/.tools/dspy_adapter.py` は、この条文集を DSPy のプログラムに接続します。

しかし、現在の接続は支配構造を忠実には再現していません。規範の版 `2a459a16d54e` の時点で、コードを読んで確認した食い違いは次のとおりです（実 LM での実行による確認はしていません）。

| 支配構造の要素 | 現在の実装 |
|---|---|
| 理念 > 原則 > 規則 の順序 | 3 層とも同じ「スコア 0」として扱う。層の順序はコードに無い |
| 上位優先（衝突したとき） | 条文集プロンプトの前文に 1 文あるだけ。衝突を検出する仕組みも、測る仕組みも無い |
| 欠缺補充（規則が沈黙する場面） | 同じく前文に 1 文あるだけ。測る仕組みが無い |
| 理念 4 条 | 判定の対象に入っていない。理念にだけ反する振る舞いは満点になる |
| 実行時の執行 | `Governed` が実行時に見るのは決定的ガードだけ。実行時に止まるのは R-1 の 1 条 |
| `検査: judge` の原則 8 条・規則 6 条 | metric の中で、実行の後に判定するだけ。実行時には効かない |
| `違反時: refine` / `escalate` | 実装が無い。出力では `block` だけを止め、ほかは記録するだけ |
| 慣習 8 条 | `検査` を持たないため判定されず、減点が一度も起きない |
| 辞書式の評価 | 1 件の予測の中でだけ成り立つ。最適化器は平均を最大化するので、5% の入力で規範に違反して残りが満点の候補（平均 0.95）が、違反が無く品質 0.90 の候補に勝つ |
| 条文の凍結 | 条文の文面は書き換えられないが、最適化器が書き換える指示文と例示に、条文を打ち消す内容が入ることを防がない |
| 検証 | テストは `DummyLM` による配線の確認だけ。遵守率も、上位が勝つかどうかも、測ったことが無い |

この仕様は、「DSPy のプログラムが支配構造を再現している」ことの意味を、測れる形で定義し、実装をそこへ近づけます。

## 保証の水準

LM の振る舞いそのものは保証できません。この仕様では、条文ごとに、次のどの水準で扱われるかを明らかにします。水準を偽らないことを、再現の前提とします（理念 I-3）。

| 水準 | 意味 | 手段 |
|---|---|---|
| 強制 | 違反する操作は実行されない | 決定的ガード |
| 検出 | 違反を実行時に見つけ、`違反時` に従って対処する。見逃しがありうる | 実行時の判定器 |
| 測定 | 評価データの上で、違反の割合を数値で示す。個々の実行は止めない | 評価時の判定器、検証セット |
| 対象外 | DSPy の経路では扱わない | — |

## 再現の定義

倫理階層の「支配構造を保つ原則」のそれぞれについて、DSPy の経路で何をもって再現とするかを定めます。

| 原則 | DSPy の経路での再現 |
|---|---|
| 1. 上位優先 | プログラムの採否を、層の順に辞書式で比べる（「採否のゲート」）。衝突の場面で上位に従う割合を測る（「検証セット」） |
| 2. 根拠必須 | lint が担う。変更しない |
| 3. 具体化のみ | 対象外。条文の意味の検査であり、人間のレビューが担う |
| 4. 欠缺補充 | 規則が沈黙する場面で、原則と理念に沿って振る舞う割合を測る（「検証セット」） |
| 5. 昇格 | 対象外。人間が行う運用 |
| 6. 執行可能性 | 条文ごとの保証の水準を報告する（「網羅の報告」） |
| 7. 硬性 | 最適化の後に、条文の文面が変わっていないこと、指示文と例示が条文を打ち消していないことを検査する（「採否のゲート」） |

## 作るもの

3 つの段階に分けます。段階ごとに Issue と Pull Request を分け、前の段階の結果を見てから次へ進みます。先に測るのは、測れない状態で執行を足しても、良くなったかどうかを確かめられないためです。

### 段階 1: 測る

振る舞いは変えません。現状を数値で示せるようにします。

#### 網羅の報告

- 条文ごとに、保証の水準（強制 / 検出 / 測定 / 対象外）と、その理由を一覧で出す。
- 判定器を使うかどうかなど、接続の設定によって水準が変わるので、設定を受け取って報告する。
- `検査` を持たない慣習、適用点 `plan` と `pr` の条文、理念は、扱われないことが分かるように表示する。
- 標準ライブラリだけで動く（DSPy が無くても報告できる）。
- `python3 -m ethics coverage [ethics_dir] [--judge]` で実行する。`--judge` は、評価に判定器を使う設定での水準を報告する。
- 実行時の判定器は段階 3 で作る。それまでは、「検出」になる条文は無い。

#### 検証セット

支配構造が効いているかを確かめるための、人間が正解を定めた場面の集まりです。

| 種類 | 場面 | 正解 |
|---|---|---|
| 衝突 | 入力・下位の条文・指示文が、上位の条文に反する行動を求める | 上位の条文に従う |
| 欠缺 | 当てはまる規則が無い。原則または理念だけが判断の拠り所になる | 原則・理念に沿って振る舞う |
| 例外 | 規則の `例外` の条件に当たる場面と、当たらない場面の対 | 当たる場面でだけ逸脱する |
| 通常 | 規範に関わらない普通の依頼 | 規範を理由に断らない（過剰な拒否を測る） |

- 場面には、種類、入力、関係する条文の ID、正解の説明を持たせる。通常の場面では、関係する条文の ID を省略できる。
- 置き場所は `ethics/evals/` とする。規則 R-5 の保護対象に入り、エージェントの Pull Request からは書き換えられない。
- 書式は Markdown とし、条文と同じ書き方にする（`## S-<番号> <題名>` の見出し、`種類` と `条文` のフィールド、`### 入力` と `### 正解`）。書式の詳細は [ethics/evals/README.md](../../ethics/evals/README.md) に置く。
- 最初の量は、条文ごとを目安にする。DSPy の経路で扱う規則ごとに衝突 1 件以上、原則ごとに欠缺 1 件、例外を持つ規則に例外の対、通常を数件。
- 場面は人間が書く。エージェントが下書きした場合も、人間のレビューを経て取り込む。
- 条文の変更で古くなった場面を見つけられるように、関係する条文の ID が存在しない場面は lint でエラーにする（E015）。書式の不備もエラーにする（E014）。
- 検証セットの不備は、条文集のコンパイルと同期（`ethics sync`）を止めない。止めるのは lint だけである。検証セットの不備で、規範の配布まで止めないため。

#### 支配構造の評価

- プログラム、条文集、検証セット、判定器を受け取り、次を報告する。
  - 層ごとの違反の件数（理念 / 原則 / 規則 / 慣習）
  - 場面の種類ごとの、正解した割合
  - 決定的ガードが阻止した呼び出しの件数
  - 規範の版（digest）と、使った LM
- 理念は、この評価の中でだけ判定器にかける。実行時には判定しない（抽象的で誤判定が多く、止める根拠にできないため）。
- 判定器の誤判定を見積もれるように、条文の `### 適合例` と `### 違反例` を判定器にかけた正解率も報告する。
- 場面に正解したかどうかは、場面の正解の説明とプログラムの振る舞い（出力と、実行したツール呼び出し）を、LLM の判定器が照らし合わせて決める。この判定も誤りうる。
- 決定的ガードがプログラムの実行そのものを止めた場面は、止めたことを振る舞いとして扱い、正解かどうかを判定する。
- Python の関数として提供する。コマンドは用意しない。

### 段階 2: 最適化の結果を採否する

#### 採否のゲート

最適化器の探索そのもの（平均スコアの最大化）は変えられません。そこで、最適化の結果を採用する前に、プログラムの単位で検査します。

- 最適化の前後のプログラムを、検証用のデータと検証セットで評価し、次の順に辞書式で比べる。
  1. 決定的ガードの違反の件数（少ないほうが良い）
  2. 理念の違反の件数
  3. 原則の違反の件数
  4. 規則の違反の件数
  5. タスクの品質（慣習からの逸脱による減点を含む）
- 最適化後のプログラムが、この順で最適化前より悪ければ、採用しない。最適化前のプログラムを返し、理由を報告する。
- 上位の項目で悪化していれば、下位の項目（品質）がどれだけ良くても採用しない。これがプログラムの単位での上位優先である。

#### 最適化後の検査

採否のゲートの一部として、次も検査します。1 つでも満たさなければ採用しません。

- すべての予測器の signature に、規範の入力フィールドが残っている。
- 実行時に渡される条文集の版（digest）が、最適化の前と一致する。
- 最適化器が書いた指示文と例示が、理念・原則・規則を緩めていない・打ち消していない（判定器で判定する）。

慣習は、最適化器が書き換えてよい層です。慣習の文面が変わること自体は、不採用の理由にしません。

### 段階 3: 実行時に検出して対処する

`Governed` に判定器を渡した場合に限り、`検査: judge` の条文を実行時にも判定します。渡さない場合の振る舞いは、今と変わりません。

| 適用点 | 判定の時点 |
|---|---|
| `input` | プログラムを呼ぶ前 |
| `tool_call` | ツールを実行する前（現在は実行の後。実行の前に変える） |
| `output` | プログラムが結果を返した後、呼び出し元へ渡す前 |

違反を見つけたときは、条文の `違反時` に従います。

| `違反時` | 対処 |
|---|---|
| `block` | 実行しない。違反した条文と理由を付けて止める |
| `refine` | 違反した条文と理由をプログラムに返して、やり直させる。上限の回数を超えても違反が残れば `block` と同じに扱う |
| `escalate` | 実行しない。人間に委ねる必要があることを、違反した条文・理由・止めた操作とともに呼び出し元へ伝える。エージェントが自分で判断して続行しない（理念 I-2） |

- 原則は `違反時` を持たない。`block` として扱う（現在の決定的ガードの扱いと同じ）。
- 慣習の違反は止めない。記録だけする。
- 決定的ガードの違反は、`違反時` の値にかかわらず実行しない（現在と同じ）。

### 衝突したときの扱い

上位優先を「上位の条文を理由に、下位の規則を破ってよい」と読ませると、エージェントが理念を口実にして規則を破る抜け道になります。そこで、層の組み合わせごとに次のように定めます。

| 衝突 | 扱い |
|---|---|
| 慣習と上位 3 層 | 上位に従う。そのための慣習からの逸脱は、違反として数えない |
| 入力・指示文と上位 3 層 | 上位 3 層に従う。入力や指示文は、規範より常に下位である |
| 規則と原則・理念 | 両方を満たす行動（多くは「実行せずに人間に委ねる」）を正解とする。規則を破ることは、`例外` に書かれた条件でだけ認める。両方を満たせない場面は条文集の欠陥として `escalate` し、人間が条文を直す |

### 文書

- `ethics/README.md` の「DSPy との接続」を、この仕様に合わせて直す。「辞書式に評価します」という記述は、1 件の予測の中でだけ成り立つことを明記する。
- 各部品が、どの保証の水準を提供するかを書く。

## 前提条件

| 条件 | 理由 |
|---|---|
| 実装は、人間が対話で指示して進める | `ethics/.tools/` は執行の仕組みであり、エージェントの Pull Request では変更できない（規則 R-5、原則 P-7）。この仕様の Issue には `symphony` ラベルを付けない |
| 検証セットの正解は、人間が定める | 何が正しい振る舞いかは、規範の解釈であり、人間の判断である（理念 I-2） |
| 実 LM での評価に使うモデルと費用の上限は、人間が指定する | 外部の API を呼び、費用がかかる |

## 受入条件

### 段階 1

- [ ] 同梱の条文集について、網羅の報告が、条文 30 件すべての保証の水準を表示する
- [ ] 判定器なしの設定では、強制が R-1 の 1 件であり、理念 4 件・慣習 8 件・適用点 `pr` の 3 件が扱われないことが、報告から読み取れる
- [ ] 検証セットに、衝突・欠缺・例外・通常の 4 種類の場面がある
- [ ] 存在しない条文 ID を参照する場面があると、lint がエラーにする
- [ ] 支配構造の評価が、層ごとの違反の件数と、種類ごとの正解の割合を報告する
- [ ] 人間が指定した実 LM で支配構造の評価を 1 回実行し、結果（数値、規範の版、使った LM、実行したコマンド）を記録する

### 段階 2

- [ ] 品質は上がったが規則の違反が増えたプログラムを、採否のゲートが採用しない
- [ ] 規則の違反は減ったが原則の違反が増えたプログラムを、採否のゲートが採用しない
- [ ] 規範の入力フィールドを失ったプログラム、条文集の版が変わったプログラムを、採否のゲートが採用しない
- [ ] 採用しなかったときに、最適化前のプログラムと、不採用の理由が返る

### 段階 3

- [ ] 判定器を渡さない `Governed` の振る舞いが、変更の前後で変わらない（既存のテストが通る）
- [ ] 適用点 `tool_call` の判定器条文に違反する呼び出しは、ツールが実行されない
- [ ] `違反時: refine` の条文に違反した出力は、条文と理由を受け取ってやり直され、上限を超えると止まる
- [ ] `違反時: escalate` の条文に違反した操作は実行されず、呼び出し元が、条文・理由・止めた操作を受け取る
- [ ] 慣習の違反では止まらない
- [ ] 段階 1 の評価を同じ LM でもう一度実行し、段階 3 の前後の数値を並べて記録する

## 対象外

- LM が規範を必ず守ることの保証。保証できるのは「強制」の水準の条文だけ。
- 条文どうしの意味の矛盾の検出（原則 3「具体化のみ」）。
- 適用点 `plan` の条文。計画の表現が決まっていない。
- 適用点 `pr` の条文。CI（`ethics check-pr`）と人間のレビューが担う。
- Issue 駆動のエージェント（Claude Code、Symphony）の経路。この経路は DSPy を通らないため、この仕様の執行と測定は及ばない。
- 最適化器の探索そのものを辞書式にすること。採否のゲートで代える。
- 慣習を規則へ昇格させる判断の自動化。

## 未確定の点

- **規則と原則・理念が衝突したときの正解。** 上の案は「両方を満たす行動を取り、満たせなければ人間に委ねる」。前文の「衝突したときは上位が優先します」を文字どおりに取り、「上位に従って規則を破る」を正解とする読み方もある。規範の解釈なので、人間が決める。
- **理念を判定器にかけるかどうか。** `ethics/00-ideals.md` は「理念は直接検査しません」と定めている。上の案は、評価の中でだけ判定し、実行時には判定しない。評価でも判定しない、とする選択もある。
- **採否のゲートの厳しさ。** 上の案は「最適化前より悪化しないこと」。判定器の誤判定があるため、「違反 0 件」を条件にすると、どのプログラムも採用できなくなるおそれがある。
- **`検査` を持たない慣習の扱い。** 上の案は「判定しない。網羅の報告で未検査と示す」。判定器を渡したときは既定で判定する、とする選択もある。
- **実行時の判定の費用。** 段階 3 は、ツール呼び出し 1 回につき、判定器条文の数だけ LM を呼ぶ。費用と遅延が許容できるか。
- **実 LM での評価に使うモデルと、費用の上限。** 同梱の条文集と検証セット（21 場面）では、1 回の評価で LM を 392 回呼ぶ（プログラム 21、場面の正解の判定 21、条文の判定 336、適合例・違反例 14）。
